## Product groups (C1)

**Definition.** A product group is a set of products whose production databases may share pool instances because they have:
1. the same MySQL major version and compatible minor-version/maintenance policy;
2. a compatible maintenance window and change calendar;
3. a similar workload profile (OLTP vs reporting/batch) and criticality;
4. no contractual or regulatory reason to be separated.

**Assignment.** Each product's catalogue entry names its group (`database.pool_group`). The platform team assigns it at product onboarding using the four rules, and records the reason. Changing group = migration PR.

**Split rule.** A product leaves its group's shared pool(s) and gets its own pool(s) when **any** of these holds:
- its tenant databases would fill ≥ 50% of a pool on their own;
- it needs a different MySQL version, flags or maintenance window;
- its load (CPU p95, IOPS, connections) is > 50% of a shared pool's budget;
- a customer contract requires it (then the dedicated tier, ADR-004, may be more appropriate).

Non-prod pools are shared by all products per environment while products share one MySQL major version **[A17]**; otherwise one non-prod pool set per version.

## How pool projects are sharded

- Prod and non-prod pools live in separate projects (`plt-sql-prd-NN`, `plt-sql-nonprd-NN`).
- A new pool project is opened when the current one reaches the **planning ceiling of 100 instances** (DR replicas included). The documented limit is up to 1,000 per project, but a smaller ceiling limits blast radius and keeps IAM policies small.
- Pool projects are aligned to product groups where possible (e.g. `plt-sql-prd-01` holds the pools of groups 1–2). The workload connect group is scoped per pool project (ADR-009 rev. 2), so a workload can only attempt connections to instances in its own pool project.
- **Fallback if test T-G2 fails** (a group-inherited `cloudsql.instanceUser` does not work for individually created IAM database users): each pool project's allow policy must list the SAs individually. T7 shows that this exceeds 1,500 principals from about 200 customers × 5 products. Pool projects would then be sharded by SA count (≤ ~700 tenant databases per pool project with an app SA plus a migration SA), raising the infrastructure project count to roughly 3–15.

## MySQL-specific operational implications

- **Table limit (M4):** 50,000 tables per instance by default. A product with ~2,000 tables per tenant database caps a pool at ~20 tenants regardless of CPU. Products must declare their approximate table count in the catalogue.
- **Connections:** MySQL uses a thread per connection. The connection budget is enforced at two layers: application pool sizes × replica caps, and per-account `MAX_USER_CONNECTIONS` (validation test T-M3).
- **IAM logins:** Cloud SQL for MySQL documents a limit of 12,000 IAM database logins per minute per instance. This matters only for very spiky Cloud Run scale-outs; connectors reuse connections.
- **Cloud Run built-in connection:** documented at 100 connections per Cloud SQL database; `max_instances` × pool size must stay below it.
- **Non-transactional DDL:** a failed MySQL migration can leave a partial schema change. Prod migrations therefore require an on-demand backup and expand/contract migrations (database architecture §7).
- **Maintenance:** one maintenance event affects every tenant on a pool. That favours Enterprise Plus for prod pools, which Google positions for near-zero-downtime planned maintenance **[Q16]**.

## Shared and Cohort models – what the savings really mean (C3)

The ~40% reduction in T1 comes **only** from the illustrative 60/20/20 model mix with 3 cohorts. It is **not a planned saving** until product teams confirm which products are multi-tenant by design **[Q1]**. Four different quantities must not be confused:

| Quantity | Dedicated | Shared / Cohort |
|---|---|---|
| Customer subscriptions | 1 per customer-product | **Unchanged** |
| Infrastructure deployments (namespaces, Cloud Run services, MIGs) | 1 per subscription per environment | 1 (Shared) or 1 per cohort per environment – **this is what drops** |
| Customer-specific databases | 1 per subscription per environment | **Unchanged in count** – one MySQL database per tenant on the product's own instance (MySQL has no row-level security, so database-per-tenant is the recommended pattern) |
| Per-customer workload identities | 1 per subscription per environment | **None** – one product identity reads every tenant's database; isolation moves into application code |
| Application replicas | Sized per customer; idle minimums per deployment | Sized by total load; saves idle minimums, **not** load-driven capacity |

**Extra responsibilities that come with Shared/Cohort products:** tenant resolution in every request path; tenant-scoped data access in every query and cache key; per-tenant rate limiting (one noisy customer affects all); per-tenant encryption and export/delete tooling; security review and penetration testing of tenant isolation; one version for everyone (Shared) or a cohort-management process (Cohort).
