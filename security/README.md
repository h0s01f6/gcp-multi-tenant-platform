## D5 – organisation and folder policies

Policies sit at the highest node where they hold. The org baseline covers keys (no SA key creation/upload), the allowed member domain, no default networks, no external VM IPs, OS Login, Shielded VM, no serial port, uniform bucket access, public-access prevention, Cloud SQL private IP only, no authorised networks, Cloud Run ingress internal / via load balancer, and cross-project SA attachment off. Tier folders add the **tier boundary** (prd folders may only use `net-host-prd` subnets and vice versa) and prod-only tightening (Cloud Run VPC egress, CMEK). Checker rules:

| Rule | Check |
|---|---|
| OP01 / OP02 | Known constraint, correct shape for its type; known node; one policy per node and constraint |
| OP03 | Baseline / mandatory constraints are set at the organisation |
| OP04 | Prod ≥ non-prod strictness; tier-scoped constraints name only their own tier |
| OP05 | A child that relaxes its parent needs `exception: {reason, approved_by, review_by}` |
| OP06 | High-impact constraints (locations, peering, Shared VPC subnets, VPC egress, CMEK) start in **dry-run** with a validation item |
| OP07 | Mandatory constraints are never relaxed below the organisation, even with an exception |
| OP08 | No unknown placeholders |

Constraint names are as listed in Google's constraint reference at the time of writing; Google is moving some to `*.managed.*` names (for example `iam.managed.disableServiceAccountKeyCreation`), so T-O1 lists the available constraints in the real organisation before apply.

## D8 – namespace baseline

Per tenant namespace, created by the namespace module before any workload: Namespace (registry labels, Pod Security `restricted`), `default` SA without token automount, one KSA per Workload Identity binding (D2), RoleBindings derived from the access-matrix `k8s:` grants (never ClusterRoleBindings), six NetworkPolicies (default-deny, same-namespace, kube-dns, GKE metadata server, Google APIs + Cloud SQL range, load-balancer sources), ResourceQuota (no LoadBalancer / NodePort services) and LimitRange. `k8s/edit` maps to `platform-tenant-edit`, not the built-in `edit`, because `edit` can delete NetworkPolicies and edit ServiceAccounts. Generator checks KB01–KB06; policy constraints in `policies/k8s/`.

**Consequence for Stage 6 Helm charts:** charts must not create ServiceAccounts, NetworkPolicies, Roles/RoleBindings or quota objects, must reference images by digest, must name the serving port `http`, and must list HTTPRoute hostnames explicitly.

## D6 – CI/CD identities and Workload Identity Federation

Every pipeline SA in the access matrix has exactly one entry in `cicd-identities.yaml`: either **WIF** (a CI job exchanges its GitHub OIDC token in `ci-pool` in `bootstrap-seed`) or **attached** (`sqlboot-*`, `isotest-*` run as Cloud Run jobs inside the VPC, started by `tf-<tier>` with `roles/run.invoker`). No keys anywhere.

- The provider accepts only tokens from our GitHub organisation (numeric owner id) and, for environment `prd`, only jobs running the central reusable workflows (`platform-workflows`).
- A principalSet can bind one attribute value and attributes are pool-wide, so the provider maps a composite **`attribute.gate = <repository id>:<environment>:<ref class>`**; each SA is bound to exact gate values (CI05: no gate reaches two tiers).
- Write-capable identities: only from their tier's reviewed environment on `main` (`prd`/`org`: 2 reviewers, no self-review). The build identity: only `main` or `v*` tags. Read-only `tf-plan-<tier>` identities (new) serve PR plans from any branch through `plan-<tier>` environments, so a PR never receives a write-capable identity.
- `tf-org@bootstrap-seed` (new) applies the org stacks (folders, D5 org policies, org IAM, D7 PAM entitlements); it was implied by `tfstate-org` but had no identity.
- Runner machines (`runner-build/-nonprd/-prd`) hold no grants (CI06).

## D7 – Privileged access

| Path | Mechanism | Duration | Approval |
|---|---|---|---|
| Org admin | PAM `pam-org-admin` (org) | 2 h | security-audit |
| Prod support write | PAM `pam-prd-support-write` (one entitlement on `tenants-prd`, one on `platform-prd`) | 4 h | platform-admins |
| Prod secret values | PAM `pam-prd-secret-write-<product>` (secretVersionAdder, conditioned to the product's secrets) | 1 h | prd operators |
| DBA admin (MySQL group auth) | Time-bound membership of `grp-hum-dba-prd-admin`, added by security-audit (group manager of that group only) after dba-lead approval (K21) | 4 h, expiry mandatory | dba-lead |
| Break-glass | Two sealed, non-federated super-admin accounts with hardware keys and no IAM roles add a named engineer to `grp-hum-prd-breakglass` with an expiry (K25) | 8 h | two-person rule |

Checker PA01–PA07 ties every entitlement to the matrix `jit` grants, forbids self-approval, requires justification and notification, and lists the alerts D10 must implement (`required_alerts`).

## D9 – Secrets, keys, supply chain

- **Secrets:** one container per customer-product-environment secret in the customer's project (`<product>-<env>-<name>`), user-managed replication in `asia-south1`, CMEK in prod. Terraform creates containers only – never versions – so no value reaches state (which `tf-plan-*` can read). Values are added by the product team (`secretVersionAdder`, limited by IAM condition to the product's secrets; prod via PAM).
- **Keys:** prod customer keys `kr-<tenant>-prd-as1/<product>-prd` in the customer's project (Q13 baseline); pooled Cloud SQL instance keys in `shr-security` (`kr-plt-prd-as1/<pool>`); 90-day rotation, 30-day destroy schedule; only service agents can encrypt/decrypt. **Correction K23:** CMEK provides per-customer revocation (crypto-shredding), not a second access check.
- **Supply chain:** build gates in `shr-build` → attestation by attestor `built-by-shr-build` (HSM EC P-256 key; only `builder` can sign). Binary Authorization project policies **enforce** in every prod project running GKE or Cloud Run and run **dry-run** in non-prod (unsigned dev snapshots). Cloud Run prod must use the project policy (`run.allowedBinaryAuthorizationPolicies`); MIG VMs boot only `shr-build` images (`compute.trustedImageProjects`) – both added to D5 in dry-run. Break-glass deployments are allowed and alerted (AL-BINAUTHZ-BREAKGLASS).

## D10 – Audit logging and security alerts

Only Cloud Audit Logs, Cloud Logging and Cloud Monitoring (already in the Stage 2 design) are used. An org-level aggregated sink sends all audit logs, plus shared Workspace login/admin events, to the locked bucket `org-audit-locked` in `shr-security`; only `grp-hum-security-audit` reads it. Data Access logs are on where data, secrets, keys and tokens are touched, with no exempted principals. Fourteen log-based alert policies implement every alert D7 requires plus detection for the Stage 3 risks; `tools/monitoring/drift.py` implements the nightly cross-tenant IAM (DR01) and workload-group (DR02) drift checks. Alert list and severities: [`../documentation/stage-3-security-implementation.md`](../documentation/stage-3-security-implementation.md) §5.
